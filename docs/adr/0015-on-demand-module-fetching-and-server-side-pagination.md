# ADR 0015: On-Demand Activity Module Fetching and Server-Side Pagination

## สถานะ
ยอมรับ (Accepted) — 2026-10-05

## บริบทและปัญหา (Context)
เมื่อนำระบบขึ้นใช้งานบน Production Server (`https://servicehub.behn.go.th`) เจ้าหน้าที่ผู้ใช้งานพบปัญหาเมื่อคลิกเมนูใน Sidebar (เช่น `#/module/waterway-cleanings` หรือหมวดงานบริการอื่น ๆ):
- หน้าจอแสดงข้อผิดพลาด: **"โหลดหน้าไม่สำเร็จ กรุณาลองใหม่อีกครั้ง หากยังพบปัญหาให้ติดต่อผู้ดูแลระบบ [ลองอีกครั้ง]"**
- ใน Developer Tools Console พบข้อผิดพลาด HTTP Status 403 และ 429 สะสมกว่า 122 รายการ

จากการตรวจสอบเชิงลึก พบสาเหตุทางสถาปัตยกรรมดังนี้:
1. **การโหลดข้อมูลแบบเหวี่ยงแห (Overfetching All 9 Modules):**
   - เมื่อผู้ใช้เข้าสู่หน้างานบริการใดหน้าหนึ่ง โค้ดเดิมได้เรียกฟังก์ชัน `allPages()` เพื่อดึงข้อมูลงานบริการทั้ง 9 หมวด พร้อมข้อมูลอ้างอิงทั้งหมดลงมาเก็บในหน่วยความจำของเบราว์เซอร์
   - หากแต่ละหมวดมีข้อมูลหลายหน้า จะเกิดคำขอ HTTP ส่งไปยังเซิร์ฟเวอร์พร้อมกันนับสิบหรือร้อยคำขอ (122 requests)
2. **การชนกับระบบสิทธิ์ (RBAC 403 Forbidden):**
   - เจ้าหน้าที่บางท่านได้รับสิทธิ์เฉพาะหมวดงานของตนเอง เมื่อระบบหน้าบ้านพยายามโหลดทั้ง 9 หมวด เซิร์ฟเวอร์จึงปฏิเสธคำขอของหมวดที่ไม่มีสิทธิ์ด้วย HTTP 403
   - ส่งผลให้ `Promise.all` ล้มเหลว และเราเตอร์ดักจับเป็นข้อผิดพลาด แสดงหน้าจอ "โหลดหน้าไม่สำเร็จ"
3. **การชนเพดานจำกัดคำขอ (Rate Limiter 429 Too Many Attempts):**
   - คำขอจำนวนมากในเสี้ยววินาทีทำให้โควตา 60 คำขอ/นาที หมดลงทันที
4. **การประมวลผลค้นหาและแบ่งหน้าบนเบราว์เซอร์ (Client-side Pagination & Filtering):**
   - การดึงข้อมูลทั้งหมดมาคำนวณแบ่งหน้าและกรองบนฝั่งเบราว์เซอร์สิ้นเปลืองแบนด์วิดท์และทรัพยากรเครื่องลูกข่ายโดยไม่จำเป็น

## การตัดสินใจ (Decision)

### 1. โหลดข้อมูลเฉพาะหมวดที่เปิดใช้งานแบบ On-Demand
- ปรับหน้ารายการทั้ง 9 หมวดให้เรียก `GET /api/activities/{module}` เฉพาะหมวดที่ผู้ใช้คลิกเปิด
- ส่งพารามิเตอร์ `page`, `per_page=6`, `q`, `from`, `to`, `sort` และฟิลด์อ้างอิงไปยัง API ฝั่งเซิร์ฟเวอร์
- ใช้ข้อมูลจาก `meta` (`total`, `current_page`, `last_page`) ที่เซิร์ฟเวอร์ส่งกลับมาในการแสดงจำนวนรายการและปุ่มเปลี่ยนหน้า

### 2. หน้ารายละเอียดและแก้ไขดึงเฉพาะรายการตาม ID
- ดึงข้อมูลผ่าน `GET /api/activities/{module}/{id}` โดยตรง
- โหลดข้อมูลอ้างอิง (`cleaning-zones` หรือ `waste-types`) เฉพาะที่หมวดนั้นต้องใช้ผ่าน `loadActivityReferences(module)`
- เมื่อบันทึก สร้าง หรือลบรายการ ให้เปลี่ยนเส้นทางไปยังหน้าเป้าหมายโดยไม่ต้องดึงทั้ง 9 หมวดซ้ำ

### 3. คำนวณจำนวนการใช้งานข้อมูลอ้างอิงฝั่งเซิร์ฟเวอร์ (`usage_count`)
- ใน `ReferenceRecordController.php`: คำนวณ `usage_count` (นับเฉพาะรายการที่ `deleted_at IS NULL`) ส่งกลับมาใน API ข้อมูลหลัก
- เก็บ `referenced_count` สำหรับตรวจสอบความปลอดภัยก่อนลบข้อมูล (Delete Protection)
- หน้ารายการและรายละเอียดข้อมูลหลัก (`cleaning-zones`, `waste-types`) อ่าน `usage_count` จาก API โดยตรง แทนการโหลดรายการงานบริการทั้งหมดมานับในเบราว์เซอร์

### 4. ปรับปรุงการจัดการ HTTP 429 และกลไก Cooldown
- ถอดรหัสค่า `Retry-After` (วินาที) จาก Header ของ HTTP 429
- แสดงข้อความภาษาไทยระบุเวลาที่ต้องรอก่อนลองใหม่อย่างชัดเจน
- ปิดกั้นการกดปุ่ม "ลองอีกครั้ง" ชั่วคราวจนกว่าจะพ้นช่วงเวลา Cooldown เพื่อป้องกันการส่งคำขอซ้ำอัตโนมัติ

### 5. ข้อตกลงสถาปัตยกรรม (Architectural Invariants)
- คงขีดจำกัดความถี่คำขอของ API ไว้ที่ 60 คำขอต่อนาทีตามเดิม
- ไม่เปลี่ยนแปลงโครงสร้างฐานข้อมูลและระบบสิทธิ์ผู้ใช้งาน (RBAC)

## ผลลัพธ์ (Consequences)
- **ลดจำนวนคำขอลงกว่า 95%:** การเปิดหน้าหมวดงานบริการ 1 หน้า ใช้คำขอเพียง 1 คำขอ (หรือ 2 คำขอหากมีข้อมูลอ้างอิง) จากเดิมที่ส่งมากกว่า 100 คำขอ
- **สลับหน้าจอได้อย่างรวดเร็ว:** การเปลี่ยนหน้าผ่าน Sidebar ตอบสนองทันทีโดยไม่ติด Rate Limit 429
- **ผู้ใช้ที่มีสิทธิ์บางหมวดใช้งานได้ราบรื่น:** ไม่เกิดข้อผิดพลาด 403 จากการแอบโหลดหมวดอื่นที่ไม่มีสิทธิ์
- **รองรับข้อมูลขนาดใหญ่ (Scalability):** การค้นหาและแบ่งหน้าทำที่ฐานข้อมูล MariaDB จึงรองรับข้อมูลหลายหมื่นรายการได้อย่างมีประสิทธิภาพ

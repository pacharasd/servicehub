# ตรวจความเร็ว ServiceHub

เป้าหมายบน Plesk หลัง PHP ทำงานอุ่นแล้ว: p95 ของรายการ/ค้นหางานบริการไม่เกิน 1,000 มิลลิวินาที และ p95 ของแดชบอร์ด/รายงานไม่เกิน 2,000 มิลลิวินาที ใช้บัญชีที่มีสิทธิ์และข้อมูลจำนวนใกล้เคียงการใช้งานจริงในการวัด คง API rate limit 60 คำขอต่อนาที

## วัดก่อนและหลัง deploy

1. บันทึก commit SHA ของ revision ที่กำลังวัด หาก revision นั้นมีสคริปต์นี้ ให้รัน `php scripts/profile-service-queries.php road-washings ถนน` จากโฟลเดอร์โปรเจกต์ คำสั่งนี้อ่านฐานอย่างเดียวและรายงานจำนวนคิวรี เวลา SQL และเวลา controller แบบ p50/p95 โดยใช้สิทธิ์ของบัญชี super-admin ที่เปิดใช้งาน ไม่ผ่าน HTTP middleware หรือเครือข่าย
2. หากมี cookie jar ของ session ที่ได้รับอนุญาตและจำกัดสิทธิ์ไฟล์ไว้ รัน `php scripts/benchmark-api.php https://servicehub.behn.go.th /path/to/private-cookies.txt road-washings ถนน` เพื่อวัด HTTP จากเครื่องเดียวกัน สคริปต์ไม่แสดง cookie หรือข้อมูลตอบกลับ และหยุดเมื่อ session หมดอายุหรือพบ 429 ลบไฟล์ cookie jar หลังใช้งาน ห้ามเก็บใน Git
3. เก็บผลก่อน deploy หากเข้าถึง revision เดิมได้ แล้วรันคำสั่งเดิมหลัง deploy และหลัง warm-up หาก revision เดิมไม่มีสคริปต์หรือเข้า CLI ไม่ได้ ให้บันทึกว่าไม่มี baseline ก่อน deploy อย่ารัน benchmark หลายชุดพร้อมกัน: หนึ่งชุดส่ง 44 คำขอ ซึ่งอาจชนเพดาน 60 คำขอต่อนาทีเมื่อมีผู้ใช้อื่นอยู่
4. สำหรับคิวรีที่ยังช้า ตรวจ MariaDB slow query log และ `EXPLAIN` ด้วยค่าตัวกรองที่เกิดจริงก่อนเพิ่มดัชนี ค้นหาแบบ `LIKE '%คำ%'` อาจสแกนตารางแม้มีดัชนีปกติ ห้ามเพิ่มดัชนีจากผลของฐานขนาดเล็กเพียงอย่างเดียว

การจับ p95 จาก 10 ตัวอย่างในสคริปต์เป็นการตรวจคร่าว ๆ; ใช้ log จากการใช้งานจริงหลายช่วงเวลาประกอบก่อนสรุปผล คำสั่ง profile วัดเวลาใน PHP CLI ส่วน benchmark วัดเวลาคำขอ HTTP ทั้งหมด จึงนำตัวเลขสองชุดมาหักลบกันเป็นเวลาเครือข่ายโดยตรงไม่ได้

## ผลตรวจบน XAMPP ระหว่างพัฒนา

- ฐานท้องถิ่นมี `road_washings` 18 รายการ, `waste_collections` 15 รายการ และ `septic_treatments` 7 รายการ จึงไม่ใช้เป็นหลักฐานว่าบรรลุเป้าหมายบน Plesk
- `EXPLAIN` ของการกรองช่วงวันที่บน `road_washings` เลือกดัชนี `road_washings_date_del_idx`; ค้นหา `LIKE '%ถนน%'` บนข้อมูล 18 รายการเลือกสแกนตาราง ยังไม่มีเหตุผลพอให้เพิ่ม migration ดัชนี
- หลังแก้ไข การวัดจาก CLI บน XAMPP: รายการ 5 คิวรี, ค้นหา 6 คิวรี, แดชบอร์ด 28 คิวรี, รายงาน 28 คิวรี สำหรับบัญชี super-admin ที่เห็นครบ 9 หมวด ตัวเลขเวลาเครื่องนี้อยู่ในหลักมิลลิวินาทีและไม่แทนผลบน Plesk
- รอบนี้ยังไม่มีช่องทาง CLI ไป Plesk จึงยังไม่ได้วัด p95, SQL time หรือสถานะ OPcache บนเซิร์ฟเวอร์จริง

## ขั้น deploy และการตั้งค่า

หลัง deploy code และ asset ให้ตรวจ PHP version, `APP_DEBUG=false`, PHP OPcache ของ PHP handler ที่เว็บไซต์ใช้ใน Plesk แล้วรัน `php artisan optimize` ในโฟลเดอร์โปรเจกต์ คำสั่งนี้สร้าง cache ของ config, events, routes และ views ตามแนวทาง [Laravel 12](https://laravel.com/framework/docs/12.x/deployment#optimization) โปรเจกต์อ่าน `env()` จากไฟล์ config เท่านั้น จึงรองรับ config cache หากเปลี่ยน `.env` ต้องสร้าง cache ใหม่ ไม่ใช้ `optimize:clear` เป็นขั้นตอนปกติเพราะจะล้าง cache driver ด้วย

ตรวจ HTTP ของ HTML และ asset ผ่าน CLI หลัง deploy และคง Vite bundle แบบเดิมสำหรับ Plesk หากยังไม่มีสิทธิ์เข้าถึง Plesk ให้ระบุผล p95/SQL บนเซิร์ฟเวอร์ว่า “ยังไม่ได้วัด” แทนการใช้ตัวเลข XAMPP อ้างว่าเร็วตามเป้าหมาย
